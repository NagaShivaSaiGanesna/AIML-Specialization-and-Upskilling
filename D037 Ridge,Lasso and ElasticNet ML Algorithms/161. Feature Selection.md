## 1. Data Preparation: The Final Cleanup

Before the model can learn, we must handle any remaining non-numerical data and prevent **Data Leakage**.

* **Binary Encoding:** We converted the `Classes` column into a numerical format ($0$ for Not Fire, $1$ for Fire). Using `.str.contains('not fire')` ensures that even "dirty" strings (with extra spaces) are captured correctly.
* **The Golden Rule of Train-Test Split:** We split the data *before* feature selection and scaling.
* **Training Set (75%):** Used to "teach" the model and calculate scaling parameters (mean, standard deviation).
* **Test Set (25%):** A "hold-out" set that stays in a vault, only used to evaluate final performance.



---

## 2. Feature Selection: Tackling Multicollinearity

In the Algerian Forest Fire dataset, many features are mathematically related (e.g., DMC, DC, and BUI are all parts of the same index). If we keep features that are too highly correlated, the model becomes unstable.

### The Correlation Threshold Strategy

We developed a function to identify features with a **Correlation Coefficient** greater than $0.85$.

* **Result:** Features like `BUI` and `DC` were identified as redundant.
* **Action:** We dropped these redundant columns from both the training and testing sets. This reduces the **Complexity** of the model and makes it faster and more interpretable.

---

## 3. Feature Scaling: Why Standardization?

Linear models (like Ridge and Lasso) are sensitive to the **scale** of the data. For example, Temperature might range from $20-40$, but Fuel Moisture could range from $0-100$.

### Standard Scaler ($Z$-Score Normalization)

We applied the **StandardScaler** to transform our features such that they have a Mean ($\mu$) of $0$ and a Standard Deviation ($\sigma$) of $1$:

$$z = \frac{x - \mu}{\sigma}$$

* **Fit vs. Transform:**
* `fit_transform()` is used on **X_train** (to learn the $\mu$ and $\sigma$).
* `transform()` is used on **X_test** (using the *same* $\mu$ and $\sigma$ learned from the training set).
* **Crucial:** Never `fit()` on your test data—this is a primary source of **Data Leakage**.



---

## 4. Visualization: The Effect of Scaling

Our side-by-side **Boxplots** revealed the immediate impact of standardization:

* **Before Scaling:** Features had wildly different ranges and units.
* **After Scaling:** All features are now on the same "playing field," centered around zero. This allows the gradient descent algorithm to converge much faster.

## 5. FAANG-Level System Design & "What If" Questions

### "What If" Scenarios

1. **What if you used `fit_transform` on the entire dataset *before* splitting?**
* This is a "Hard Fail" in interviews. Your training set would "know" the mean and range of the test set, leading to over-optimistic results that fail in production.


2. **What if you set your Correlation Threshold to $0.50$ instead of $0.85$?**
* You would lose too much information. While you'd have no multicollinearity, you'd likely end up with **Underfitting** because you deleted features that actually helped predict FWI.


3. **What if the FWI (target) is also highly skewed?**
* Standardization is for *input* features. For the *target*, should you use a **Log Transformation** or a **Power Transformer**? (Hint: Think about how it affects the Mean Squared Error).



### System Design Question: The Feature Store

* **The Scenario:** You have hundreds of forest stations sending data. Instead of calculating the `StandardScaler` every time, you want to store these "scaling parameters" ($\mu$ and $\sigma$) globally.
* **The Task:** Design a **Feature Store** service. When a new sensor comes online, how does it retrieve the correct scaling parameters? How do you handle "Versioning"—what if the weather patterns change significantly over 10 years and you need to re-calculate the mean?

## 1. The "What If" Scenarios

### Q1: What if you used `fit_transform` on the entire dataset before splitting?

**The Answer:** This leads to **Data Leakage**.

* **The Reason:** `StandardScaler` calculates the mean and standard deviation of whatever data it sees. If it sees the whole dataset, your training data "borrows" information from the future (the test set). When you later evaluate the model, your test results will be artificially high, but the model will perform poorly on real, new data because it was "cheating" during the scaling phase.

### Q2: What if you set your Correlation Threshold to 0.50 instead of 0.85?

**The Answer:** You would likely cause **Underfitting**.

* **The Reason:** A correlation of 0.50 means there is only a moderate relationship between features. By dropping everything above 0.50, you are deleting a massive amount of unique "signal." While you would have zero multicollinearity, your model wouldn't have enough information to capture the complexity of forest fire physics, leading to high bias and poor predictions.

### Q3: What if the FWI (target) is also highly skewed?

**The Answer:** You should consider a **Log Transformation** or **Box-Cox Transformation** on the target.

* **The Reason:** Linear Regression assumes that the residuals (the errors) are normally distributed. If your target is highly skewed, your errors will likely be skewed too. Transforming the target helps "squeeze" the outliers and makes the relationship more linear, which often results in a lower and more stable **Mean Squared Error (MSE)**.

## 2. System Design: The Feature Store

### Designing a Scalable Feature Store

In a FAANG-level environment, you don't store scaling parameters in a local pickle file; you use a **Feature Store** (like AWS SageMaker Feature Store or Tecton).

1. **Metadata Management:** Store the $\mu$ (mean) and $\sigma$ (standard deviation) as versioned assets in a database (e.g., DynamoDB).
* *Schema:* `{ "feature_name": "temp", "version": "v2026", "mean": 32.5, "std": 4.1 }`


2. **Versioning & Drift:** Weather patterns change over decades (Climate Drift).
* **The Task:** Implement a **Model Monitoring** service that checks if the incoming data distribution still matches the "v2026" parameters. If the mean shifts significantly (e.g., global warming increases average temp), the system triggers a "Re-training Pipeline" to update the scaling parameters and create "v2027."


3. **Real-Time Retrieval:** When a sensor in the forest sends a raw value, the **Inference Service** calls the Feature Store API to get the latest version of the scaling parameters, applies the $Z$-score formula, and then passes the standardized value to the model.

## 3. Summary of Preparation Logic

| Step | FAANG Best Practice | Why it Matters |
| --- | --- | --- |
| **Train-Test Split** | Always split *before* any calculation. | Prevents Data Leakage. |
| **Correlation Drop** | Only drop "Redundant" signal ($>0.85$). | Maintains model "signal" while improving stability. |
| **Standardization** | Fit on Train, Transform on Test. | Ensures the model treats units (Celsius vs. %) fairly. |
| **Boxplot Audit** | Visualize before and after scaling. | Confirms that the scaling math actually worked as intended. |
