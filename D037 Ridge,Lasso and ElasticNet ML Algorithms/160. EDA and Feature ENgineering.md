
## 1. Feature Engineering: Encoding & Dropping

Before feeding data into a model (especially **Ridge** or **Lasso**), we must ensure the data is strictly numerical and relevant.

* **Dropping Temporal Columns:** We removed `Day`, `Month`, and `Year`.
* **Why?** In a general regression model, we want to predict FWI based on *weather conditions* (Temperature, Humidity), not just because it is "August 15th." This prevents the model from simply memorizing a date.


* **Encoding the Target (Classes):** We transformed the `Classes` column into binary labels:
* **Fire:** 1
* **Not Fire:** 0


* **Cleaning Category Strings:** We encountered a classic real-world issue: hidden spaces in strings (e.g., `"fire "` vs `"fire"`). Using `.str.contains('not fire')` is a robust way to handle these inconsistencies.

## 3. Limitations and Assumptions

* **Linearity Assumption:** By using Ridge/Linear Regression, we are assuming that the relationship between Temperature and FWI is a straight line. If the relationship is actually exponential, our model error (MSE) will stay high.
* **Outlier Sensitivity:** Our boxplot showed several outliers in the **FWI** index. Since Ridge Regression uses **Squared Errors** ($L2$), it is sensitive to these outliers. We may need to investigate if these are "true" fire events or data entry errors.
* **Independence of Observations:** We assumed each day is independent. In reality, if it was hot yesterday, it’s likely hot today (**Auto-correlation**). Regression models don't naturally "know" about time order.

## 1. The "What If" Scenarios

### Q1: What if `DC` and `BUI` have a 0.98 correlation?

**The Problem:** This is "near-perfect" multicollinearity. The two variables are essentially providing the exact same information.

* **Ridge (L2):** It will retain both but halve the importance (coefficients) between them. While this makes the model stable, it keeps redundant data.
* **Lasso (L1):** This is the superior choice here for **simplification**. Lasso will look at the 0.98 correlation and simply set one of them (the one slightly less predictive) to **zero**. This results in a cleaner, more interpretable model.

### Q2: What if the model fails on one region but succeeds on the other?

**The Problem:** Your model has "memorized" regional patterns instead of "learning" fire physics.

* **The Fix:** You must use **Stratified K-Fold Cross-Validation** (treating 'Region' as a strata) or **GroupKFold**. By ensuring every "Fold" contains a mix of both Bejaia and Sidi Bel Abbes data, the model is forced to find the universal weather patterns that cause fires in *both* places, rather than relying on regional biases.

### Q3: What if you predict "Fire/No Fire" instead of FWI?

**The Answer:** You would switch from **Linear/Ridge Regression** to **Logistic Regression**.

* **The Cost Function Shift:** You move from minimizing **Mean Squared Error (MSE)**, which measures distance, to minimizing **Log-Loss (Cross-Entropy)**. Log-loss penalizes the model based on how "confident" it was in the wrong prediction (e.g., predicting 99% chance of Fire when it was actually Not Fire).

## 2. System Design: The "Auto-Janitor" Service

### Designing the Regex-based Encoding Service

To build a scalable "Auto-Janitor" that handles global forest data, you would implement the following architecture:

1. **The Pattern Registry:** Instead of hard-coding "fire" or "not fire," maintain a dictionary of regular expressions (Regex) for different languages.
* *Fire Patterns:* `r"fire|fuego|aatash|incendio"`
* *Not Fire Patterns:* `r"not\s*fire|no\s*fuego|safe"`


2. **The Normalization Engine:** * **Step 1:** Lowercase all strings and strip whitespace.
* **Step 2:** Apply the Regex patterns.


3. **Handling "Unknowns" or Missing Labels:**
* **Strategy A (Strict):** If a label doesn't match any pattern, move the row to a "Manual Review" queue and exclude it from the training set to avoid poisoning the model.
* **Strategy B (Imputation):** Use the other weather features to *predict* the missing label using a secondary "filler" model (K-Nearest Neighbors), but flag these as "estimated" in the database.

## 3. Summary of Feature Engineering Decisions

| Action Taken | Technical Justification |
| --- | --- |
| **Dropping Day/Month/Year** | Prevents the model from overfitting to specific dates; focuses on meteorological signal. |
| **`.str.strip()` on Columns** | Prevents `KeyError` exceptions during feature selection and model training. |
| **Binary Encoding (0/1)** | Converts categorical "Classes" into a format readable by mathematical cost functions. |
| **`.str.contains()`** | A robust way to handle "dirty" strings with inconsistent spacing or hidden characters. |
