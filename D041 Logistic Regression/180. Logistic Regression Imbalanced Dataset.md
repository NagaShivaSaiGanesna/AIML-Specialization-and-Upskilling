# Logistic Regression for Imbalanced Datasets

## 1. What is an Imbalanced Dataset?

In a **binary classification** problem, you have two output classes (e.g., 0 and 1). A dataset is called **imbalanced** when the proportion of samples across these classes is highly skewed — one class dominates the other.

### Formal Definition

Given a dataset of $N$ total samples with two classes $C_0$ and $C_1$:

$$\text{Imbalance Ratio} = \frac{|C_0|}{|C_1|}$$

If this ratio is significantly greater than 1 (e.g., 99:1), the dataset is **imbalanced**.

**Example from this lecture:**
- Total samples: $N = 10{,}000$
- Class 0 (majority): $9{,}846$ samples
- Class 1 (minority): $154$ samples
- Imbalance ratio $\approx 64:1$

### Balanced vs. Imbalanced — Quick Comparison

| Property | Balanced Dataset | Imbalanced Dataset |
|---|---|---|
| Class ratio | Approximately 1:1 | Highly skewed (e.g., 99:1) |
| Model bias | Learns both classes equally | Biased toward majority class |
| Accuracy metric | Reliable | Misleading (high accuracy, poor recall) |
| Typical use | General classification | Fraud detection, rare disease diagnosis |

---

## 2. Why Does Imbalance Hurt Standard Logistic Regression?

Logistic regression minimises the **log-loss (cross-entropy)**:

$$\mathcal{L} = -\frac{1}{N} \sum_{i=1}^{N} \left[ y_i \log(\hat{p}_i) + (1 - y_i) \log(1 - \hat{p}_i) \right]$$

Because the majority class contributes far more terms to this sum, the model is mathematically incentivised to predict the majority class for nearly every input. It can achieve very high accuracy simply by **always predicting class 0**, while completely failing to detect class 1 — which is usually the class we care about most (e.g., fraud, cancer, default).

---

## 3. The Solution: `class_weight` in Logistic Regression

Scikit-learn's `LogisticRegression` provides a `class_weight` parameter that modifies the loss function by assigning a **penalty multiplier** to each class.

### How It Works

The modified loss becomes:

$$\mathcal{L}_{weighted} = -\frac{1}{N} \sum_{i=1}^{N} w_{y_i} \left[ y_i \log(\hat{p}_i) + (1 - y_i) \log(1 - \hat{p}_i) \right]$$

where $w_{y_i}$ is the weight assigned to the true class of sample $i$.

By setting $w_1 \gg w_0$, every misclassification of a minority-class sample is penalised much more heavily, forcing the model to pay attention to it.

### Two Ways to Set `class_weight`

**Option A — `"balanced"` (Automatic)**

Scikit-learn computes weights automatically using:

$$w_c = \frac{N}{k \cdot |C_c|}$$

where $k$ is the number of classes and $|C_c|$ is the count of samples in class $c$. This is a good default starting point.

```python
from sklearn.linear_model import LogisticRegression

model = LogisticRegression(class_weight="balanced")
```

**Option B — Manual Dictionary (Recommended for Fine-Tuning)**

You specify exact weights per class:

```python
# Give class 1 ten times more importance than class 0
model = LogisticRegression(class_weight={0: 1, 1: 10})
```

## 4. End-to-End Implementation Walkthrough

### Step 1 — Create an Imbalanced Dataset

```python
from sklearn.datasets import make_classification
from collections import Counter

X, y = make_classification(
    n_samples=10_000,
    n_features=2,
    n_informative=2,
    n_redundant=0,
    n_clusters_per_class=1,
    weights=[0.99],          # 99% of samples belong to class 0
    random_state=10
)

print(Counter(y))
# Counter({0: 9846, 1: 154})
```

### Step 2 — Visualise

```python
import seaborn as sns
import matplotlib.pyplot as plt

sns.scatterplot(x=X[:, 0], y=X[:, 1], hue=y)
plt.title("Imbalanced Dataset")
plt.show()
```

### Step 3 — Train/Test Split

```python
from sklearn.model_selection import train_test_split

X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.25, random_state=42
)
```

### Step 4 — Hyperparameter Tuning with GridSearchCV

The key insight here is treating `class_weight` as a hyperparameter and searching over it along with other logistic regression parameters.

```python
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import GridSearchCV, StratifiedKFold

# Define the parameter grid
param_grid = {
    "penalty": ["l1", "l2"],
    "C": [0.01, 0.1, 1, 10],
    "solver": ["liblinear", "saga"],
    "class_weight": [
        {0: 1, 1: 1},    # equal importance
        {0: 1, 1: 10},   # class 1 ten times more important
        {0: 1, 1: 50},   # class 1 fifty times more important
        {0: 1, 1: 100},  # class 1 hundred times more important
        "balanced"       # automatic balancing
    ]
}

# StratifiedKFold preserves class ratios in each fold — critical for imbalanced data
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=42)

grid = GridSearchCV(
    estimator=LogisticRegression(max_iter=1000),
    param_grid=param_grid,
    cv=cv,
    scoring="f1",   # F1-score is more meaningful than accuracy here
    n_jobs=-1
)

grid.fit(X_train, y_train)
print("Best parameters:", grid.best_params_)
```

> **Why `StratifiedKFold`?** In imbalanced datasets, a random split might place *all* minority samples in the training set or test set by chance. Stratified K-Fold guarantees that each fold maintains the original class distribution.

### Step 5 — Evaluate

```python
from sklearn.metrics import accuracy_score, classification_report, confusion_matrix
import warnings
warnings.filterwarnings("ignore")   # suppress solver convergence warnings

y_pred = grid.predict(X_test)

print("Accuracy:", accuracy_score(y_test, y_pred))
print(classification_report(y_test, y_pred))
print("Confusion Matrix:\n", confusion_matrix(y_test, y_pred))
```

## 5. Understanding the Evaluation Metrics

For imbalanced datasets, **accuracy alone is deceptive**. The metrics that matter are:

### Precision and Recall

Given:
- **TP** = True Positives (minority class correctly identified)
- **FP** = False Positives (majority class wrongly flagged as minority)
- **FN** = False Negatives (minority class missed)

$$\text{Precision} = \frac{TP}{TP + FP}$$

$$\text{Recall (Sensitivity)} = \frac{TP}{TP + FN}$$

$$\text{F1 Score} = 2 \cdot \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

### Why Recall Matters More Here

In applications like fraud detection or medical diagnosis, a **False Negative** (missing a fraudulent transaction or a disease) is far more costly than a **False Positive**. Increasing `class_weight` for the minority class trades some precision for higher recall — a deliberate and often correct trade-off.

| Metric | What it answers | Imbalanced dataset importance |
|---|---|---|
| Accuracy | Overall correct predictions | **Misleading** — use with caution |
| Precision | Of all positive predictions, how many were right? | Moderate |
| Recall | Of all actual positives, how many did we catch? | **Critical** |
| F1 Score | Harmonic mean of precision and recall | **Best single metric** |

## 6. Limitations, Assumptions & Pitfalls

- **Accuracy is not your friend.** A model that predicts class 0 for every sample achieves 98.5% accuracy on this dataset but has 0% recall for class 1. Always report F1, precision, and recall.

- **`class_weight="balanced"` is not always optimal.** The automatically computed weights are a good baseline, but the best weights are data-dependent and should be tuned via cross-validation.

- **StratifiedKFold is non-negotiable.** Using standard `KFold` on imbalanced data can produce folds with zero minority-class samples, making validation completely unreliable.

- **Logistic regression assumes linear separability.** If the minority class is not linearly separable from the majority class in feature space, no amount of class weighting will compensate. Consider non-linear models or better feature engineering.

- **High class weight ≠ always better recall.** Setting an excessively high weight for the minority class can cause the model to over-correct — flagging nearly every sample as minority class, which destroys precision and makes the model practically useless.

- **`class_weight` is not the only tool.** Techniques like SMOTE (Synthetic Minority Over-sampling Technique), random undersampling, and ensemble methods (e.g., BalancedRandomForest) are complementary approaches and may outperform simple reweighting in highly imbalanced scenarios.

- **Solver and penalty compatibility.** Not all solvers support all penalty types. For example, `solver="liblinear"` supports `l1` and `l2`, while `solver="lbfgs"` only supports `l2`. Mismatching them will raise an error.

## 7. FAANG-Level Q&A

**Q1. What if the minority class is so rare that even after applying `class_weight`, the model still fails to learn it (e.g., 1 positive in 10,000 samples)?**

When the imbalance is extreme (beyond roughly 1:1000), `class_weight` alone is often insufficient because the decision boundary has almost no positive samples to learn from. In this case, combine reweighting with **oversampling** (e.g., SMOTE generates synthetic minority samples) or **undersampling** the majority class. Alternatively, use anomaly detection framing (e.g., One-Class SVM, Isolation Forest) rather than standard binary classification, as the problem is better modelled as "detect rare events" rather than "classify two balanced groups."

---

**Q2. What if you use `class_weight` but evaluate using accuracy — will the reported score be trustworthy?**

No. Accuracy computes $\frac{TP + TN}{N}$, which is dominated by the majority class. A model that correctly classifies all 9,846 majority samples but misses every minority sample still reports $\approx 98.5\%$ accuracy. This is known as the **accuracy paradox**. The correct scoring metric during cross-validation should be `f1`, `roc_auc`, or `average_precision` (area under the precision-recall curve), especially when the minority class is what you actually care about predicting.

---

**Q3. What if the best `class_weight` found by GridSearchCV is `{0: 1, 1: 50}`, but at deployment the class imbalance changes (e.g., fraud rate drops from 1.5% to 0.1%)?**

The optimal `class_weight` is calibrated to the training distribution. If the real-world imbalance shifts significantly, the model's decision threshold and class weights become miscalibrated, leading to either too many false positives or missed detections. The correct approach is **model recalibration**: re-tune the `class_weight` parameter (or decision threshold) on recent data that reflects the new distribution. Building a **monitoring pipeline** that tracks precision and recall in production will surface such drift automatically before it causes business impact.

---

**Q4. You are building a real-time fraud detection system at a bank processing 50 million transactions per day. How would you design the training pipeline to handle class imbalance at scale?**

At that volume, storing and retraining on all data is impractical. The architecture should use a **two-stage approach**: (1) an offline batch pipeline running weekly that trains a logistic regression (or gradient boosted tree) with `class_weight="balanced"` on a stratified sample — e.g., all positive (fraud) cases plus a random 5% of negatives — stored in a distributed store like Apache Parquet on S3; (2) an online learning layer that fine-tunes the decision threshold daily using the previous day's labelled feedback via a streaming platform (Kafka + Spark Structured Streaming). The evaluation dashboard should track $\text{F1}$, $\text{Recall}@\text{Precision}=0.9$, and false-negative rate per transaction category in real time, with automated alerts triggering retraining when recall drops below an SLA threshold. Model serving should be behind a feature store (e.g., Feast) to ensure consistent feature computation between training and inference.
