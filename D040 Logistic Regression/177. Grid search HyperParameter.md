# Hyperparameter Tuning with GridSearchCV and Cross-Validation

## Overview

When training machine learning models, there are two categories of parameters:

- **Model parameters** — learned automatically from data during training (e.g., weights in logistic regression).
- **Hyperparameters** — set *before* training begins and control *how* the model learns (e.g., regularization strength, solver algorithm).

**Hyperparameter tuning** is the systematic process of searching for the optimal combination of hyperparameters that maximizes model performance on unseen data. Without it, you are essentially guessing — and different datasets will respond best to different configurations.

---

## Why Random State Matters

Before diving into tuning, it is worth understanding why model performance appears to fluctuate without any code changes.

When you split a dataset using `train_test_split`, the `random_state` parameter controls *which samples* fall into the training set versus the test set. Changing `random_state` produces a completely different split, which changes the score — not because the model improved, but because the evaluation data changed.

> **Key insight:** A model score evaluated on a single fixed split is not a reliable estimate of true generalization. This is precisely the problem that **cross-validation** solves.

---

## Key Hyperparameters in Logistic Regression

Before tuning, you must understand *what* you are tuning. The table below covers the main hyperparameters of `LogisticRegression` in scikit-learn.

| Hyperparameter | Description | Common Values |
|---|---|---|
| `penalty` | Regularization type (controls overfitting) | `'l1'` (Lasso), `'l2'` (Ridge), `'elasticnet'`, `None` |
| `C` | Inverse of regularization strength. Smaller `C` = stronger regularization. | `0.01, 0.1, 1.0, 10, 100` |
| `solver` | Optimization algorithm used to find model weights | `'newton-cg'`, `'lbfgs'`, `'liblinear'`, `'sag'`, `'saga'` |
| `class_weight` | Handles class imbalance | `None`, `'balanced'` |

### The Regularization Parameter C

Regularization adds a penalty to the loss function to prevent overfitting. In logistic regression, the loss with L2 regularization is:

$$\mathcal{L} = \sum_{i=1}^{n} \log\left(1 + e^{-y_i \mathbf{w}^T \mathbf{x}_i}\right) + \frac{\lambda}{2} \|\mathbf{w}\|^2$$

The `C` parameter in scikit-learn is defined as:

$$C = \frac{1}{\lambda}$$

So a **large C** means weak regularization (model fits training data closely), and a **small C** means strong regularization (model is more constrained and generalized).

### Solver Selection Guide

| Solver | Best For |
|---|---|
| `liblinear` | Small datasets; supports L1 and L2 |
| `lbfgs` | Default; works well for L2, multiclass |
| `newton-cg` | Multiclass classification, L2 only |
| `sag` / `saga` | Large datasets (faster convergence); `saga` supports L1 |

## Cross-Validation: The Foundation

### Why Cross-Validation?

A single train/test split produces a score that depends heavily on *which* samples ended up in each partition — a high-variance estimate. **K-Fold Cross-Validation** solves this by evaluating the model on $k$ different, non-overlapping subsets of the data.

### K-Fold Cross-Validation

The dataset is divided into $k$ equal folds. The model is trained $k$ times, each time using $k-1$ folds for training and 1 fold for validation. The final score is the mean across all folds:

$$\text{CV Score} = \frac{1}{k} \sum_{i=1}^{k} \text{Score}_i$$

### Stratified K-Fold Cross-Validation

In standard K-Fold, the class distribution in each fold may be uneven — especially harmful with imbalanced datasets. **Stratified K-Fold** guarantees that each fold preserves the same class proportion as the full dataset.

For example, if 30% of your data is class 1, every fold will also contain approximately 30% class 1 samples. This makes the cross-validation estimate far more reliable for classification tasks.

```python
from sklearn.model_selection import StratifiedKFold

cv = StratifiedKFold(n_splits=5, shuffle=False)
```

## GridSearchCV: Exhaustive Hyperparameter Tuning

### How It Works

**GridSearchCV** performs an exhaustive search over a specified parameter grid. It evaluates *every possible combination* of hyperparameter values using cross-validation and returns the combination that produces the best score.

If you define:
- 4 values for `penalty`
- 5 values for `C`
- 5 values for `solver`

GridSearchCV evaluates:

$$4 \times 5 \times 5 = 100 \text{ combinations}$$

Each combination is trained and evaluated $k$ times (once per CV fold), so the total number of model fits is:

$$\text{Total fits} = 100 \times k$$

With $k = 5$, that is **500 model fits**.

### Implementation

```python
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import GridSearchCV, StratifiedKFold

# Step 1: Define the hyperparameter grid
penalty_values = ['l1', 'l2', 'elasticnet']
C_values = [100, 10, 1.0, 0.1, 0.01]
solver_values = ['newton-cg', 'lbfgs', 'liblinear', 'sag', 'saga']

params = dict(
    penalty=penalty_values,
    C=C_values,
    solver=solver_values
)

# Step 2: Define base model and cross-validation strategy
model = LogisticRegression()
cv = StratifiedKFold(n_splits=5, shuffle=False)

# Step 3: Initialize GridSearchCV
grid = GridSearchCV(
    estimator=model,
    param_grid=params,
    scoring='accuracy',
    cv=cv,
    n_jobs=-1        # Use all available CPU cores
)

# Step 4: Fit on training data
grid.fit(X_train, y_train)

# Step 5: Inspect results
print(grid.best_params_)   # e.g., {'C': 0.01, 'penalty': 'l1', 'solver': 'saga'}
print(grid.best_score_)    # e.g., 0.92

# Step 6: Predict on test data
y_pred = grid.predict(X_test)
```

> **Important:** The parameter names in `dict()` must exactly match the argument names in the scikit-learn model. A typo like `'penality'` will raise an error.

### GridSearchCV vs. RandomizedSearchCV

| Feature | GridSearchCV | RandomizedSearchCV |
|---|---|---|
| Search strategy | Tries every combination | Samples a random subset of combinations |
| Computation time | High (exhaustive) | Lower (configurable via `n_iter`) |
| Guarantee | Finds the best among defined grid | May miss the best, but faster |
| Best for | Small grids, critical tuning | Large grids, quick exploration |

**RandomizedSearchCV** is covered in the next session. It is preferred when the hyperparameter search space is large, because it randomly samples `n_iter` combinations rather than trying all of them — achieving comparable results in a fraction of the time.

---

## Interpreting Results

After fitting, GridSearchCV exposes:

- `grid.best_params_` — the winning hyperparameter combination
- `grid.best_score_` — the mean cross-validated score of the best combination
- `grid.cv_results_` — detailed results for every combination tried

The best model is automatically refitted on the full training set using the best parameters, so `grid.predict()` and `grid.predict_proba()` are ready to use directly.

---

## Limitations, Assumptions & Pitfalls

- **Combinatorial explosion:** Adding even one new hyperparameter with 5 values multiplies the total search space by 5. For large grids, GridSearchCV becomes computationally prohibitive — prefer RandomizedSearchCV instead.
- **Not all combinations are valid:** Certain solver–penalty combinations are incompatible (e.g., `newton-cg` does not support L1 penalty). scikit-learn will raise an error. Always verify compatibility in the documentation before defining your grid.
- **Best CV score ≠ best test score:** Cross-validation score is an estimate of generalization; slight overfitting to the validation folds is still possible, especially with very small datasets.
- **`n_jobs=-1` on shared machines:** Using all CPU cores can freeze a shared server or cloud instance. Use `n_jobs=2` or `n_jobs=4` in such environments.
- **Scoring metric matters:** Optimizing for `accuracy` on an imbalanced dataset is misleading. Use `f1`, `roc_auc`, or `average_precision` when class distribution is skewed.
- **Data leakage risk:** Never include the test set during GridSearchCV. The grid must be fit only on training data; the test set is used once — at the very end — for final evaluation.

## FAANG-Level Q&A

**Q1. What if your dataset is severely imbalanced (e.g., 95% class 0, 5% class 1) — how does this affect GridSearchCV with `scoring='accuracy'`?**

Accuracy is a deceptive metric on imbalanced data: a model that always predicts class 0 achieves 95% accuracy while being completely useless. GridSearchCV would select hyperparameters that essentially learn to ignore the minority class. You should use `scoring='f1'`, `'roc_auc'`, or `'average_precision'` instead, and pair it with `StratifiedKFold` to ensure the minority class is represented in every fold. Additionally, setting `class_weight='balanced'` in `LogisticRegression` adjusts the loss function to penalize misclassifying the minority class more heavily.

---

**Q2. What if you have a continuous hyperparameter like `C` — is a discrete grid always the right approach?**

A discrete grid can miss the true optimum lying between two tested values (e.g., the best `C` might be `0.035` when you only tested `0.01` and `0.1`). For continuous hyperparameters, `RandomizedSearchCV` with a statistical distribution (e.g., `scipy.stats.loguniform`) is more effective — it samples values from a continuous range rather than fixed points. Alternatively, **Bayesian optimization** libraries such as `Optuna` or `scikit-optimize` model the performance surface probabilistically and converge to the optimum with far fewer evaluations.

---

**Q3. What if cross-validation score is high but final test accuracy is significantly lower?**

This gap indicates **overfitting to the hyperparameter search itself** — a phenomenon called *hyperparameter overfitting* or *selection bias*. It occurs when the search space is very large relative to dataset size, causing the best-found parameters to be lucky on the validation folds but poor on truly unseen data. The correct remedy is a **three-way split**: training set (for fitting), validation set (for hyperparameter selection), and a held-out test set (touched only once at the very end). Alternatively, use nested cross-validation, where an outer loop estimates generalization and an inner loop performs the hyperparameter search.

---

**Q4. You are building a fraud detection system with 50 million transactions per day. How would you design a hyperparameter tuning pipeline at this scale?**

Running GridSearchCV on 50 million records is computationally infeasible — a single model fit could take hours. Instead, **subsample** a stratified, representative subset (e.g., 1–5 million records) for the tuning phase, then retrain the final model with the best parameters on the full dataset. Replace GridSearchCV with **Bayesian optimization** (e.g., Optuna with pruning) to evaluate only the most promising regions of the hyperparameter space, dramatically reducing the number of trials. Distribute training across a cluster using frameworks like **Dask-ML** or **Ray Tune**, which parallelize both the cross-validation folds and individual model fits. Since fraud data is highly imbalanced, `scoring` must be set to `'average_precision'` (area under the precision-recall curve), and `StratifiedKFold` is non-negotiable to ensure each fold reflects the true fraud rate. Finally, the final evaluation must be performed on a **time-based holdout set** (e.g., the most recent 2 weeks of transactions) rather than a random split, because temporal leakage — training on future data — would produce falsely optimistic results in production.
