# Deployment Guide: AWS Elastic Beanstalk & CodePipeline

This guide details the process of deploying a Flask-based Machine Learning application to the **AWS Cloud** using a **CI/CD (Continuous Integration/Continuous Deployment)** pipeline.

---

## 1. Architectural Overview
The deployment architecture connects your local development environment to the cloud using three main components:

1.  **GitHub Repository:** Acts as the "Source" of truth for your code.
2.  **AWS CodePipeline:** The "Connective Tissue" that listens for changes in GitHub and automatically pushes them to the server.
3.  **AWS Elastic Beanstalk (EB):** A **PaaS (Platform as a Service)** that provides a pre-configured Linux environment (running Python) to host your application.



---

## 2. Essential Configuration: `.ebextensions`
Elastic Beanstalk requires a specific configuration to know how to start your Python application. This is handled by a hidden folder in your root directory.

### The `python.config` file
You must create a folder named `.ebextensions` and a file inside it named `python.config`.

**File Content:**
```yaml
option_settings:
  "aws:elasticbeanstalk:container:python":
    WSGIPath: application:application
```

### Why `application:application`?
* The first `application` refers to the filename (`application.py`).
* The second `application` refers to the Flask object variable defined inside that file ($application = Flask(\_\_name\_\_)$).

## 3. Step-by-Step Deployment Workflow

| Step | Action | Key Details |
| :--- | :--- | :--- |
| **1. Commit Config** | `git add .` & `git push` | Ensure `.ebextensions` is live on GitHub. |
| **2. Create EB App** | AWS Beanstalk Console | Select **Python** as the platform. |
| **3. Configure Pipeline** | AWS CodePipeline | Select **GitHub (Version 1)** as the Source Provider. |
| **4. Trigger Webhook** | Automatic | CodePipeline connects to your repo to monitor the `main` branch. |
| **5. Skip Build** | Build Stage | Since it's a standard Python app, we skip the Build stage. |
| **6. Deploy** | Deployment Provider | Select your Elastic Beanstalk Application and Environment. |

## 4. Understanding the WSGI Path (LaTeX)
Elastic Beanstalk uses **WSGI (Web Server Gateway Interface)** to forward requests from the internet to your Python code.

The interaction can be modeled as:
$$Internet \rightarrow Nginx/Apache \rightarrow WSGI \rightarrow Flask(Application)$$

By setting the `WSGIPath`, you are telling the AWS Linux server exactly where the entry point of your code resides in memory.

## 5. Limitations, Assumptions, and Pitfalls

* **Case Sensitivity:** **Pitfall:** The folder must be named `.ebextensions` (plural). Naming it `.ebextension` will cause the deployment to ignore your config, leading to a "502 Bad Gateway" error.
* **Health Checks:** **Assumption:** AWS expects a successful `200 OK` response from your root URL (`/`). If your index page fails, AWS will mark the environment as "Severe" (Red).
* **Environment Variables:** **Limitation:** Hardcoding AWS keys or database URLs in `application.py` is insecure. Use the **Elastic Beanstalk Configuration** menu to set Environment Properties instead.
* **Timeout Errors:** **Pitfall:** Large `.pickle` files might take time to load. Ensure your instance type (e.g., t2.micro) has enough RAM to hold the model, or the deployment may time out.

## 6. FAANG-Level System Design & "What If" Questions

### System Design Questions
1.  **High Availability:** Elastic Beanstalk defaults to a single instance. How would you configure a **Multi-AZ (Availability Zone)** deployment to ensure the app stays up if an entire AWS Data Center goes offline?
2.  **Infrastructure as Code (IaC):** Instead of clicking through the AWS Console, how could you use **Terraform** or **AWS CloudFormation** to replicate this exact environment for "Staging" and "Production"?
3.  **Security:** Your `.pickle` files are currently inside the GitHub repo. How would you move them to **Amazon S3** and grant the Beanstalk instance secure access using **IAM Roles**?

### "What If" Scenarios
1.  **What if** you need to update your model weights without redeploying the entire code? Could you trigger a specific pipeline stage for just the `models/` folder?
2.  **What if** the application starts crashing only under high traffic? Which AWS tool would you use to check the logs (`tail -f`) without SSHing into the instance? (Hint: CloudWatch Logs).
3.  **What if** you wanted to implement a **Rollback**? If a new code push breaks the site, how does CodePipeline/Beanstalk allow you to return to the previous "Succeeded" version instantly?


Let's dive into these high-level architectural and "What If" questions. Answering these correctly is what separates a **Junior Developer** from a **Senior ML Systems Engineer** at companies like Amazon or Google.

## 1. FAANG-Level System Design Answers

### Q1: High Availability (Multi-AZ)
**The Challenge:** If the AWS Data Center (Availability Zone) hosting your instance loses power, your app goes down.
* **The Fix:** Change the Elastic Beanstalk (EB) "Capacity" setting from **Single Instance** to **Load Balanced**.
* **The Architecture:** Deploy instances across at least two **Availability Zones (AZs)**. The **Application Load Balancer (ALB)** sits in front, health-checking instances. If AZ-1 fails, the ALB automatically routes all traffic to AZ-2.
* **Data Persistence:** Ensure your `.pickle` models are either bundled in the deployment or stored in a **Multi-AZ S3 bucket** so every instance has access to the same model.

### Q2: Infrastructure as Code (IaC)
**The Problem:** Manual configuration in the AWS Console is prone to human error and hard to replicate for "Testing" or "Staging" environments.
* **The Solution:** Use **Terraform** or **AWS CloudFormation**.
* **How it works:** You write a script (e.g., `main.tf`) that defines your VPC, EC2 instance type, and Beanstalk environment variables. 
* **Benefit:** To create a "Staging" environment, you simply run the script again with a different variable. This ensures **Environment Parity**—your dev, staging, and prod environments are identical.

### Q3: Security (IAM Roles & S3)
**The Strategy:** Storing models in GitHub is bad practice (file size limits and security).
* **S3 Storage:** Upload `ridge.pickle` and `scaler.pickle` to a private **Amazon S3** bucket.
* **IAM Instance Profile:** Create an **IAM Role** with `AmazonS3ReadOnlyAccess` and attach it to your Elastic Beanstalk environment.
* **Code Change:** In `application.py`, use the `boto3` library to download the models from S3 into the instance's memory during the startup phase. This keeps your GitHub repository lightweight and your models secure.

## 2. "What If" Scenario Analysis

### Scenario 1: Updating Model Weights without Code Changes
* **The Solution:** Decouple the model from the code. If your code is programmed to pull the latest model from a specific **S3 URI** (e.g., `s3://my-bucket/latest/model.pkl`), you can simply overwrite the file in S3.
* **The Trigger:** You can set up an **S3 Event Notification** that triggers a Lambda function to "refresh" or "re-deploy" the Beanstalk environment whenever a new model is uploaded.

### Scenario 2: Crashing Under High Traffic (CloudWatch)
* **The Tool:** **Amazon CloudWatch Logs**.
* **The Action:** In the EB Console, enable **Log Streaming** to CloudWatch. 
* **The Insight:** You can search for "MemoryError" or "Timeout" across all instances simultaneously. If you see high CPU usage, you would adjust your **Auto-Scaling Group (ASG)** triggers to add more instances when CPU exceeds 70%.

### Scenario 3: Instant Rollbacks
* **The Feature:** Elastic Beanstalk has a built-in **"Application Versions"** dashboard.
* **The Process:** Every time CodePipeline pushes code, EB saves it as a numbered version (e.g., `v1`, `v2`).
* **The Rollback:** If `v3` breaks the site, you go to the dashboard, select `v2`, and click **"Deploy."** EB will perform a rolling update to revert all instances to the stable version in minutes.
