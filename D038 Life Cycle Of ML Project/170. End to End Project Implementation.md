# Algerian Forest Fire: End-to-End Machine Learning Web Application

This study guide outlines the process of transforming a trained Machine Learning model into a functional, professional web application using **Flask** and preparing it for **AWS Cloud** deployment.

---

## 1. The Machine Learning Project Life Cycle
Building an end-to-end project involves moving beyond a Jupyter Notebook and into a structured software development lifecycle.

### Core Stages
1.  **Data Collection:** Retrieving data from sources like **MongoDB**, **MySQL**, **Hadoop**, or CSV files.
2.  **Exploratory Data Analysis (EDA):** Understanding data distributions and relationships.
3.  **Feature Engineering:** Handling missing values, data cleaning, and **Feature Scaling** (Standardization).
4.  **Feature Selection:** Identifying significant predictors and addressing **Multicollinearity**.
5.  **Model Training:** Training and selecting the best performing model (e.g., **Ridge Regression**).
6.  **Pickling:** Saving the trained model and the scaler object as `.pickle` files for later use.
7.  **Web App Development:** Creating a user interface (UI) to interact with the model.
8.  **Deployment:** Hosting the application on a cloud provider like **AWS**.

## 3. Developing the Application Logic
The `application.py` file serves as the bridge between the user's input and the Machine Learning model.

### Key Technical Implementations
* **Renaming the Entry Point:** For **AWS Elastic Beanstalk**, it is standard practice to name the script `application.py` and the Flask object `application`.
* **Loading Pickled Objects:** Use the `pickle` library to load the model and scaler into memory once the app starts.

### Core Mathematical Concepts (LaTeX)
Before a prediction is made, the raw input $X_{raw}$ must be transformed using the saved **StandardScaler** to ensure it matches the training data distribution:

$$z = \frac{x - \mu}{\sigma}$$

Where:
* $z$ is the scaled value.
* $x$ is the original input.
* $\mu$ is the mean of the training data.
* $\sigma$ is the standard deviation of the training data.

The **Ridge Regression** model then calculates the prediction using the regularized cost function:

$$J(\theta) = \sum_{i=1}^{n} (y_i - \hat{y}_i)^2 + \lambda \sum_{j=1}^{m} \theta_j^2$$

## 5. Limitations, Assumptions, and Pitfalls

* **Pickle Versioning:** **Assumption:** The Python and Scikit-Learn versions used during training must match the deployment environment. If they differ, the pickle file may fail to load.
* **Statelessness:** **Pitfall:** Flask apps are stateless. If you update the model, you must restart the application or implement a dynamic loading mechanism.
* **Input Validation:** **Limitation:** This implementation assumes users will provide valid numerical data. Real-world apps require robust "try-except" blocks to handle non-numeric or out-of-bounds inputs.
* **Scaling Consistency:** **Crucial Step:** You must only use `.transform()` on new data, never `.fit_transform()`. Fitting on a single new data point would ruin the mean/standard deviation logic established during training.

## 6. System Design & "What If" Questions

### FAANG-Level System Design Questions
1.  **Scalability:** If this application receives 100,000 requests per second, how would you evolve the architecture beyond a single AWS Elastic Beanstalk instance?
2.  **Model Versioning:** How would you implement A/B testing to compare the performance of the current Ridge Regression model against a new Lasso or ElasticNet model in production?
3.  **Latency:** Loading `.pickle` files for every request is inefficient. How do you ensure the model stays in memory, and what are the trade-offs of using an API-based model serving tool like TorchServe or TFServing?

### "What If" Scenarios
1.  **What if** the input data contains missing values at the web-form level? How should your `application.py` handle these before passing them to the scaler?
2.  **What if** the `scaler.pickle` was lost? Could you still use the `ridge.pickle` for accurate predictions? (Hint: Think about the impact of unscaled features on coefficients).
3.  **What if** you wanted to turn this into a Batch Prediction system instead of a Real-time system? What changes would you make to the Flask routes?

## 1. FAANG-Level System Design Answers

### Q1: Scalability (100k requests/sec)
**The Challenge:** A single Flask app on Elastic Beanstalk will bottleneck due to CPU/Memory limits and the Global Interpreter Lock (GIL).
* **Decoupling:** Move the model out of the Flask app. Use **AWS SageMaker** for model hosting or a **Kubernetes (EKS)** cluster with **KServe**.
* **Load Balancing:** Use an **Application Load Balancer (ALB)** to distribute traffic across multiple "Worker" nodes.
* **Auto-Scaling:** Set up **Horizontal Pod Autoscaling (HPA)** based on request latency or CPU utilization.
* **Caching:** For common input patterns (e.g., specific regions/temperatures), use **Redis** to cache the prediction result to avoid re-running the model.

### Q2: Model Versioning & A/B Testing
* **Blue/Green Deployment:** Use a service like **AWS SageMaker Endpoints**. You can route **90%** of traffic to the "Production" (Ridge) model and **10%** to a "Canary" (Lasso) model.
* **Shadow Mode:** Send traffic to both models but only return the Ridge result to the user. Compare the Lasso results in the background to ensure parity before a full swap.
* **MLflow/DVC:** Use these tools to track which specific version of the `.pickle` file is currently "Live" so you can rollback instantly if the new model fails.

### Q3: Latency & Memory Management
* **The Problem:** Loading a pickle file on *every* request is a "Junior" mistake. It adds disk I/O latency.
* **The Fix:** Load the model as a **Global Variable** or a **Singleton Class** during the Flask startup sequence. This keeps the weights in RAM.
* **Advanced Serving:** For high-performance, convert the model to **ONNX** or **TensorRT** format. These formats optimize the math operations for the underlying hardware (CPU/GPU), reducing inference time from milliseconds to microseconds.

## 2. "What If" Scenario Analysis

### Scenario 1: Missing Values in the Web Form
* **Frontend Fix:** Use HTML `required` attributes.
* **Backend Fix:** Implement **Imputation logic** in `application.py`. If a user leaves "Rain" blank, you might default to the **median** value from your training set. 
* **Failure Mode:** If you pass a `NaN` (Not a Number) to the `standard_scaler.transform()`, it will throw an error, crashing the request for that user.

### Scenario 2: Lost `scaler.pickle`
* **The Result:** Your predictions will be **garbage**.
* **The Reason:** If the model expects "Temperature" to be between $-2$ and $2$ (scaled), but you pass a raw value of $35$ degrees, the linear equation $y = mx + b$ will produce an astronomical result. 
* **Lesson:** The Scaler is just as important as the Model. They are a "Pipeline" and should ideally be saved together as a single **Scikit-Learn Pipeline** object.

### Scenario 3: Batch Prediction vs. Real-Time
* **Architecture Change:** Instead of a single `/predict` route, you would create a `/upload` route.
* **Process:**
    1. User uploads a `.csv`.
    2. Flask saves the file to an **S3 Bucket**.
    3. An **AWS Lambda** function is triggered to process the whole file in the background.
    4. The user is notified via email or a dashboard when the results are ready.
